AI 업무 인프라는 어떻게 작동하는가 | HOW AI WORK INFRASTRUCTURE WORKS
AI 업무 인프라는 ChatGPT에 질문하고 답을 받는 구조를 넘어, 사람의 업무지시를 AI가 이해하고 필요한 자료와 업무도구에 접근한 뒤 파일·프로그램을 실행하고 변경이력을 남기며 실제 서비스까지 배포하는 연결구조입니다. 모든 업무가 같은 경로를 쓰는 것은 아니며, 이메일 요약처럼 코딩이 필요 없는 업무는 App과 Skill 중심으로, 웹사이트·프로그램 구축은 Codex 같은 실행 에이전트와 Git·GitHub·배포 계층까지 사용합니다.

사람 | HUMANCONTROL

업무의 목적·조건·우선순위·승인 기준을 정합니다. AI가 무엇을 해야 하는지 결정하는 최종 통제자입니다.

AI · WorkREASONING

ChatGPT·Claude·Gemini 등이 요청을 이해하고 조사·분석·문서작성·계획수립 등 여러 단계의 업무를 수행합니다.

Skills · InstructionsRULES

매번 같은 업무방식을 다시 설명하지 않도록 절차·금지사항·품질기준·예시를 재사용 가능한 업무규칙으로 표준화합니다.

Apps · ConnectorsCONNECTION

Gmail·Drive·Calendar·Notion·GitHub 등 실제 업무서비스를 AI와 연결하고 허용된 권한 범위에서 데이터를 읽고 처리합니다.

Codex · Code AgentsEXECUTION

Codex·Claude Code·Gemini CLI 등이 PC 폴더·코드·파일·터미널·Git 저장소를 읽고 실제 수정·실행·테스트를 수행합니다.

GitCHANGE CONTROL

AI가 무엇을 변경했는지 기록합니다. 변경 전후를 비교하고 문제가 생기면 이전 상태로 되돌릴 수 있게 합니다.

GitHubSOURCE OF TRUTH

PC의 변경이력과 프로젝트 파일을 원격 저장소에 보관하고 사람·AI·배포서비스가 함께 사용하는 기준 원본 역할을 합니다.

Cloud DeploymentSERVICE

Cloudflare Pages·Vercel·GitHub Pages 등이 GitHub의 확정된 파일을 가져와 실제 웹사이트·서비스로 배포합니다.

전체 흐름은 사람의 지시 → AI의 판단·Work → Skill의 업무규칙 → App의 외부자료 연결 → Codex 등 실행 에이전트의 파일·코드 작업 → Git의 변경기록 → GitHub의 기준원본 저장 → Cloud 배포 → 사람의 검증·승인 → 실제 업무결과로 이해하면 됩니다. AX는 단순히 AI를 사용하는 것이 아니라 사람이 하던 업무절차를 AI·데이터·도구·자동화와 연결해 하나의 수행체계로 전환하는 것입니다.

핵심 원칙: 같은 프로젝트에는 저장소를 하나만 기준 원본으로 두고, 비밀키·OAuth 토큰·비밀번호는 저장소에 넣지 않습니다. 사람은 AI가 수행한 작업의 목적·범위·변경이력·실제 반영 여부를 최종 확인합니다.

AI 코드 작업 검증·변경 통제 | CODE REVIEW · CHANGE CONTROL · TECHNICAL OVERSIGHT

생성형 AI와 코드 에이전트가 HTML·CSS·JavaScript·GitHub·배포환경을 직접 수정하는 업무에서는 사용자가 모든 코드를 직접 작성할 필요는 없습니다. 그러나 AI가 어느 파일과 계층을 수정했는지, 수정 방법이 구조적으로 적절한지, 기존 규칙을 불필요하게 덮어쓴 것은 아닌지, 변경사항이 GitHub와 실제 서비스에 정상 반영됐는지를 판별할 수 있어야 합니다. 이 장은 개발자 양성이 아니라 AI의 기술작업을 사람이 검토·승인·수정·중단할 수 있도록 하는 최소 기술 판독 및 감독 역량을 다룹니다.

12-1 시스템 계층 판독 | STRUCTURE LAYERS
오류를 고치기 전에 문제가 어느 계층에 있는지 먼저 분류합니다. 화면에 보이는 하나의 증상이라도 원인은 HTML, CSS, JavaScript, Git, Build, Deploy 또는 Cache 중 다른 곳에 있을 수 있습니다.

12-2 HTML과 DOM 구분STRUCTURE

HTML은 저장된 원본 구조이고 DOM은 브라우저가 실제로 구성한 현재 문서 구조입니다. 원본 HTML에 요소가 있는지, JavaScript가 실행 중 요소를 생성·삭제·교체하는지, ID 중복이나 selector 대상 누락이 없는지를 확인합니다. HTML을 고쳤는데 다시 원상태가 된다면 JS가 DOM을 다시 쓰는지도 봅니다.

12-3 CSS 최종 적용 규칙CASCADE

Cascade·Specificity·Inheritance·Source Order·Inline Style·!important·Media Query·Pseudo-class·CSS Variable을 구분합니다. 핵심은 “CSS를 수정했는가”가 아니라 브라우저의 computed style에서 어느 selector가 최종 승리하는가입니다. 앞 규칙의 44px이 뒤의 48px !important에 덮이면 화면은 바뀌지 않습니다.

12-4 파일 역할·기준 원본OWNERSHIP

각 기능의 기준 소유 파일을 구분합니다. 예: index.html은 문서 구조, page.css는 페이지 스타일, app.js는 동적 동작, config.js는 콘텐츠·설정입니다. 원본·생성파일·빌드결과물·공통파일·페이지전용파일·외부라이브러리를 구별하고, 원본이 존재하면 생성·빌드 결과물을 직접 수정하지 않습니다. 원칙은 하나의 관심사에 하나의 기준 소유자입니다.

12-5 Override·Patch DebtWARNING SIGNALS

!important 증가, 같은 selector의 여러 파일 반복, 단순 수정에 새 CSS·JS 생성, fix·hotfix·final·날짜 파일 누적, inline style 남용, JS로 CSS 강제 삽입, 정적 레이아웃을 MutationObserver로 보정, 유사 함수 중복, 삭제 파일의 import·캐시 규칙 잔존은 기술부채 신호입니다. 새 덮어쓰기를 추가하기보다 실제 소유 원본에서 수정합니다.

12-6 Git 변경 통제AUDIT TRAIL

Repository·Branch·Working Tree·Stage·Commit·Commit SHA·Diff·Push·Pull·Merge·Revert·Rollback의 의미를 구분합니다. git status는 변경 상태, git diff는 변경 내용, git log --oneline은 이력, git branch는 현재 branch, git rev-parse HEAD는 현재 SHA를 확인합니다. AI의 “수정 완료”와 Git 기록은 별개의 사실입니다.

12-7 Diff 범위 검토SCOPE CONTROL

수정된 파일 수, 신규·삭제 파일, 요청과 관계없는 변경, 대량 포맷팅, 자동생성 파일, package.json·lock 파일·설정·환경변수 변경을 확인합니다. 작은 문제에는 작은 diff가 정상입니다. 한 줄 수정 요청에 여러 파일이 바뀌었다면 왜 필요한지 확인하고 불필요한 변경은 되돌립니다.

12-8 Build·Deploy 판별CI/CD

Source → Commit → Push → Build → Deployment → Production → Browser를 서로 다른 단계로 봅니다. GitHub 파일이 정상이어도 잘못된 production branch, build 실패, 잘못된 output directory, 이전 SHA 배포, 환경변수 차이로 실제 화면은 달라질 수 있습니다. “현재 Production이 어느 commit SHA를 배포했는가”를 확인합니다.

12-9 권한·환경·SecretsACCESS

Repository·Organization·GitHub App·OAuth scope·Cloudflare 권한·API Key·Access Token·Environment Variable·Secret·Preview/Production 차이를 구분합니다. 접근 실패를 코드 오류로 착각하지 않습니다. 비밀정보는 코드에 넣지 않고 .env, GitHub Secrets, Cloudflare Variables 등 분리된 저장소를 사용합니다.

12-10 Cache는 마지막CACHE

원본 변경 → 올바른 파일 → override → commit → branch/push → build → deploy → production SHA를 먼저 확인한 뒤 Browser·Service Worker·CDN·Cloudflare·Build Cache를 점검합니다. “화면이 안 바뀐다 = 캐시”로 즉시 결론내리지 않습니다.

운영자는 코드를 직접 모두 작성할 필요는 없지만 아래 질문에 답할 수 있어야 합니다. 답을 확인할 수 없으면 AI에게 근거를 다시 제시하게 하고 배포·삭제·대규모 변경은 승인하지 않습니다.

계층HTML·CSS·JS·Git·Build·Deploy·Cache 중 어디의 문제인가
소유 파일AI가 수정한 파일이 해당 기능의 기준 원본인가
수정 방식원본을 고쳤는가, 새 override를 추가했는가
파일 수새 파일과 불필요한 중복이 생기지 않았는가
Diff변경범위가 실제 요청과 일치하는가
Commit정확한 branch와 SHA에 변경이 기록됐는가
검증테스트·Audit·Build 결과가 성공했는가
Production실제 배포 SHA와 화면이 GitHub 원본과 일치하는가
운영 원칙: “AI가 수정했다고 말했다”는 완료 증거가 아닙니다. 원본 소유 위치 → diff → commit → build → deploy → production을 순서대로 확인합니다. 문제가 생기면 새 CSS·JS·캐시 우회 규칙을 먼저 덧붙이지 말고 가장 가까운 기준 원본에서 원인을 수정합니다.
